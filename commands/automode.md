# 一、总则

## 【决策权】用户没授权，你就不许做决定

用户打 `/automode`，授权的只是**阶段之间自动推进**（不要问"要继续吗"），**不包括替他做任何决定**。

**什么算决定**：在两种以上可行的做法之间选一个，而且选哪个会影响产出——方案、接口、命名、范围、文案、修不修某个问题、要不要偏离规划。

**固定停点**（各阶段会再点名）：

| 编号 | 停点 | 出现在 |
|---|---|---|
| S1 | 项目里有上一轮残留的规划 / 交接文件：接着做还是丢弃 | 阶段 0 |
| S2 | 规划的「待确认问题」不是空的 | 阶段 2 |
| S3 | 实现中发现方向性分歧（定义见阶段 3） | 阶段 3 |
| S4 | 审查的 🟡 修不修 | 阶段 4 |
| S5 | 子代理缺凭据或缺前提条件 | 任何阶段 |
| S6 | 复审两轮后仍有 🔴 | 阶段 4 |
| S7 | `automode-check` 报 ❌（某个子代理用错了模型）：要不要重跑 | 任何阶段 |

另外，处于 plan 模式时阶段 -1 直接停。

**固定停点之外，凡是符合上面定义的决定，也一律先问**——尤其是你自己动手时碰到的（例：阶段 0 判成小任务直接做，改文案时挑哪种措辞）。实现子代理在规划写明的范围内做的实现细节不算，那是规划已经定了的；它要越出规划，就是 S3。

**跳过停点，只认用户在本轮亲口给的授权，而且授权只覆盖他说话时针对的那个停点。** 例：他在 S2 说「都按你的推荐来」，只管这一批待确认问题，到 S4 照样要问。要覆盖本轮后面所有停点，他必须明说「后面都不用问我」或「我不在，你一路做完」。跳过时在回复里引用原话。

被授权跳过时怎么处理：

- **S1** → 一律「接着做」，不删任何文件
- **S2、S3、S4** → 按推荐执行（规划的「暂按」、你给出的判断），决定清单里标「用户授权：『原话』」
- **S5、S6、S7** → **授权也不能跳过**，按出在哪里处理：
  - S7 出在规划或审查 → **本轮停在这一步**：不拿跑错模型的规划去实现、不拿跑错模型的审查去修，汇报等用户
  - S5、S7 出在某个实现 / 修复包 → 只把**这一包**标成阻塞、不进审查，其它包照常做，汇报里列出
  - S6 → 不进阶段 4.5，带着剩余的 🔴 汇报。**被阻塞的修复包对应的 🔴 也算 S6**——修不了的 🔴 不能悄悄漏进文档阶段

以下**都不是**跳过的理由：有默认做法；选错代价小；不算阻塞；规划里写了「暂按」；memory 或旧交接文档里他以前这么说过；他在别的停点说过「按推荐」；你觉得答案显然。

> 实测（10-08 `ff02bc08`）：planner 列了 Q1–Q6，主会话一句「都有明确的默认做法、选错代价很小，都不算阻塞问题，我直接按默认做法往下走」，19 秒后就派了实现，用户一个问题都没看到。planner 按设计给**每一条**都写了「暂按什么」和「选错的后果」——拿「有默认、代价小」当标准，就没有任何一条会停。使用方的原话是「很恐怖」。

**怎么问**：先在正文把完整信息列出来（规划全文、审查表格），再用 `AskUserQuestion` 问。第一个选项是推荐做法并标 `(Recommended)`，其余是备选，描述里写清选错的后果。一次最多 4 题、每题 2–4 个选项，多了分批问。

**提问框本身要能独立看懂**：问题文本里逐条用一句话写清「编号 + 是什么问题 + 不修会怎样」，选项描述里写清选了会发生什么。用户看提问框时可能看不到前面的正文——只给编号和短标题，等于让他没看报告就拍板。

> 实测（10-09）：审查表格放在正文、提问框里只写了「N26 替换规矩交给子代理」「N27 备份名精确到分钟」，用户的反应是「n26 和 27 你都没给我看？？」。

**谁定的要留痕**：最后汇报有一栏「决定清单」，每个决定要么是用户答的，要么是 planner 在规划第 5 节「已自行决定」里写明的（用户看过全文），要么是用户亲口授权的。三样都不是，就是你越权了——照实写出来，别藏。

## 【模型路由】只写别名，跑完核实

| 角色 | 用哪个子代理 | 模型 | 怎么指定 |
|---|---|---|---|
| 规划 | `planner-fable` | fable | frontmatter 已钉。**绝不能传 model 参数**——Agent 工具的 model 参数会覆盖 frontmatter，传了就静默降级 |
| 审查、复审 | `code-reviewer` | opus | 同上 |
| 实现、修复、文档、调研 | general-purpose / Explore | sonnet | **必须**传 `model: "sonnet"`。不传就继承主会话（opus），内置 agent 默认都是 inherit |

- **任何地方都只写别名**（fable / opus / sonnet），不写版本号。版本由 `settings.json` 的 `ANTHROPIC_DEFAULT_*_MODEL` 决定，新模型上线只改那一行，所有角色一起切。写死版本号 = 新模型出来后这个角色还停在旧版，而且不报错。
- **每个子代理返回后都核实一次，不靠配置推断**（不到 1 秒、不花 token）：

  ```bash
  node ~/.claude/plugins/model-router/automode-check.js --from <阶段 0 记下的开工时间戳>
  ```

  它从 transcript 读出窗口内每个子代理和主会话**实际**跑的模型、effort、调用次数，逐个对照上表和 env 当前钉的版本。越早发现越省：审查员跑错模型，要是到最后才发现，审查、修复、文档全得重来。没有 ❌ 和 ⚠ 时只打一行（各角色个数 + 主会话当前上下文），有问题才打完整表；最后汇报加 `--full` 打完整表贴进去。
  - 出现 ❌ → **停点 S7**：那个子代理的产出按「没按设计跑」处理，停下来问用户要不要重跑
  - 出现「版本 ≠ env」→ 会话中途改过 env 就正常；否则查是哪里写死了版本号
  - 出现「主会话窗口内有别的模型」→ 中途用 `/model` 切过，告诉用户
  - 出现「窗口内没有 planner-fable / code-reviewer」→ 本轮跳过了规划、或还没到审查就正常；否则检查时间戳

## 【派活规矩】实现、修复、文档子代理都适用

### 每个 prompt 必带九条（它会照做，但不会自己想到）

- **P1 读什么**：给绝对路径——`.automode-plan.md` 的「§2 步骤 N」，或审查报告里的 R×，或交接文件。直接用用户的 `PLAN-*.md` 时，同时给出 `.automode-plan.md`（如有）并注明「修订以它为准」。**只给路径和步骤号，不复述规划内容**——复述在贵模型上多花 output，还会丢细节
- **P2 行尾**（CRLF 项目；CLI 2.1.276 实测，CLI 升级后要重测）：
  - 改已有文件**用 Edit**：行尾统一的文件会保住 CRLF；行尾混用的文件会被整份归一成多数派
  - **Write 写出来的一律是 LF**，新建或整份重写后要转成跟同目录一致
  - 用 Python 批改别用 `read_text` / `write_text`（会静默把 CRLF 吃成 LF，`git diff` 看不出来），用 `read_bytes` / `write_bytes`
  - `.ps1` 要 UTF-8 with BOM；收尾时一次性数一遍改过的文件有没有裸 LF
- **P3 验证**：必须跑哪些命令，把实际输出贴回来
- **P4 报实际报错**：回退 / 失败验证要报真实看到的报错，不许写"应该会报错"
- **P5 返回前自查**：跑通测试、核规划点名的边界条件、查复制粘贴漏改的变量名 / 索引 / 条件。低级错误自己挡掉，别留给最贵的审查
- **P6 报告格式**：改了哪些文件（**精确到函数名或行号区间**）、跑了什么验证、**哪些没验证**、自查修了什么。这份报告直接喂给审查，越具体审查越快
- **P7 进度落盘 + 收工条款**：**每完成一个步骤**，先往 `<项目根>/.automode-handoff-<包名>.md` 追加一行进度（完成了步骤 N、改了哪些文件），再自评一次，满足任一条就收工：① 已改完约 10 个文件；② 已反复调试十几轮；③ **工具调用已上百次**。收工 = 在 handoff 里补上「还剩什么 / 下一步从哪接」后返回。半途落盘不算失败，硬撑到底才是。逐步记进度是为了进程崩溃后能接上——只在收工时才写，正常干到一半崩了就什么都没留下
- **P8 缺凭据或缺前提（S5）**：需要账号、密码、密钥而手上没有，或某个前提不满足 → **停下来回报，等用户给**。不许试密码、不许直连数据库改数据、不许绕过登录
- **P9 规划走不通（S3）**：规划和代码现状对不上，或规划的做法走不通 → **停下来回报差异和备选**，不许自己换方案

> P8、P9 最容易漏。一个被要求「做完 / 跑绿」又没有出路的子代理，必然会自己找一条走得通的路——09-16 有子代理拿不到测试账号的密码，就直连数据库把密码哈希覆盖了。**堵死一条路的同时要给出另一条。**

### 规模：每个子代理 1–3 个步骤

子代理的上下文只增不减，跑得越久每次调用越贵，成本是**超线性**的：

| 工具调用次数 | 每次调用成本 |
|---|---|
| 0–50 | 18.4k |
| 50–100 | 21.4k |
| 100–200 | 25.5k |
| 200–400 | **48.3k（2.6 倍）** |

最坏一个跑了 304 次、5 小时、上下文涨到 703k，等效 17.61M，占当天 39%。另一个只写了「约 10 个文件」没给检查点，一路跑到 251 次都没收工——所以 P7 要求**每个步骤结束自评**，不是边干边监控。

- 一个子代理负责规划 §2 里的 **1–3 个步骤**；「做个 demo」「实现整个 P3」这种整块任务，自己先拆
- 估计一包要改超过 10 个文件或调试超过 15 轮，就拆
- **`code-reviewer` 豁免**：审查天然要看大量文件，它的价值就是准确，压缩它等于白花前面所有的钱

### 中断：落了盘就新起，没落盘就续接

| 情况 | 怎么办 | 为什么 |
|---|---|---|
| 子代理按 P7 主动收工（进度已写进 handoff） | **新起一个**，prompt 给 handoff 路径 + P1–P9 | 就是要丢掉膨胀的上下文 |
| 被 429 / 503 打断（中间状态还在上下文里） | **`SendMessage` 续同一个 agent** | 新起要从头再来，审查还会漏掉追到一半的线索 |

规划、实现、审查都适用。`429 Concurrency limit` 是用户级、跨会话共享的额度；一轮里撞两次以上就退回串行。规划本来就不并行，见阶段 1「规划一次只开一个」。

### 并行：最多 2 个

必须同时满足：两包改的**文件集合完全不相交**（拿**最新**规划——阶段 2 修订过的——里每步的文件清单逐个比对，别凭印象），且**没有依赖**（B 不读 A 的结果、不用 A 新建的函数）。**拿不准就串行**：并行省几十分钟，改冲突了要返工几小时。

## 【文件约定】

| 文件 | 谁写 | 什么时候删 |
|---|---|---|
| `<项目根>/.automode-plan.md` | `planner-fable`；直接用 `PLAN-*.md` 时由主会话写一份指向它的短记录；阶段 2 / S3 的修订补充由主会话写（见阶段 2） | 阶段 5，全部完成、修订补充已并回原规划后 |
| `<项目根>/.automode-plan-redesign.md` | 阶段 2 选 B 时新起的 `planner-fable` | 并进原规划、核对完就删；阶段 5 再确认一次 |
| `<原名>.bak-<YYYYMMDD-HHMM>` | 主会话（替换规划前） | 不删，留给用户核对；汇报里列出 |
| `<项目根>/.automode-handoff-<包名>.md` | 实现 / 修复子代理按 P7 每步追加进度，收工时补剩余 | 阶段 5，对应的包确认完成后 |
| `<项目根>/code-review-<YYYYMMDD-HHMM>.md` | **主会话**（审查员只读、不能写文件） | 不删，留档；提示用户可加进 `.gitignore` |
| 项目自己的交接文档（如 `plan/新对话提示词.md`） | 阶段 0 主会话追加新需求；阶段 4.5 文档子代理 | 不删 |

## 【主会话分工】

- **你只做**：编排、跑验证命令、读结果、写审查报告文件、核实子代理的声明、把决定交给用户
- **不写生产代码。** 例外只有两种：阶段 0 判定的极小任务；下一条里用户当场提的界面小改。实测一轮主会话在 opus 上做了 35 次 Edit、19 次 Write，是最大的一笔浪费；10-19 主会话自己改了 141 次 Edit、52 次 Write，当天主会话占了 73%
- **小修补**只限：验证命令、配置值、一两行内的明显笔误；以及**用户当场提的界面小改**——单个文件里一两行的样式或措辞（对齐、间距、按钮位置、文案），而且用户已经说清要改成什么。超出这个范围（多个文件、改逻辑、要补测试、要先查原因）就派子代理。主会话改过的同样算本轮改动，进审查范围（攒批审，见阶段 4 开头）。**审查发现的问题一律派修复子代理**，不管多小
- 规划文件不是生产代码：阶段 2 里把用户的决定写进规划（修订补充、或改动集中时直接改），可以主会话自己做
- 不要先开 Explore 再转述给 planner——它自带 Read / Grep / Glob / Bash，查两遍还丢细节（实测 3 个 Explore 串行 37 分钟）。实在要开 Explore，按【模型路由】传 `model: "sonnet"`
- 子代理在后台跑，完成会通知你；等待时结束回合，别 sleep 轮询，也别去 Read 子代理的 transcript（会撑爆上下文）
- 用 `TaskCreate` / `TaskUpdate` 跟踪进度，用户在界面上能看到走到哪
- 上下文成本：按 `~/.claude/CLAUDE.md` 成本控制第 1 条——300k 和 500k 各报一次，只报信息，**不劝用户开新会话**。当前上下文看 `automode-check` 输出里的「主会话当前上下文」
- **审查报告落盘后附压缩命令（只给不催）**：审查报告每写一次（首次落盘、追加 S4 的选择、追加每一轮复审结果），之后第一次结束回合等子代理时，如果 `automode-check` 报的主会话上下文超过 300k，就在那条汇报最后附一行填好的 `/compact`，用户可以直接复制。超过 300k 后的第一个这样的点给一次，超过 500k 后的第一个再给一次，之后不再给。不解释、不劝，用户不压缩就照常往下走。压缩后 automode.md 会被自动带回来（10-14 实测），流程状态以文件为准，所以命令里只写找回状态要用的东西：

  ```
  /compact 继续 /automode：<任务一句话>。开工时间戳 <date +%s 的值>（automode-check --from 用）；现在在阶段 <X>，下一步 <Y>。以文件为准：规划 <路径>、审查报告 <路径>、交接 <路径>。在跑或要 SendMessage 续的子代理：<名字 + ID，没有写「无」>。还没问用户的：<编号，没有写「无」>
  ```

  > 10-14 实测：会话不压缩一路涨到 818k，后半程每次调用光重读上下文就要 6–8 万 EIU；手动压缩后回到约 2 万，加上自动带回的文件和 automode.md。
- **阶段顺序**：代码 → 审查 → 修复 → 然后才是文档。别被规划的节编号带偏
- **不 commit、不 push**。改动留在工作区，汇报里列出来，提不提交由用户决定
- 流程上的新经验写进本命令或 agent 定义，只记在 memory 里不算数——memory 按启动目录分，换个目录就读不到

# 二、流程

## 阶段 -1：plan 模式检查

**处于 plan 模式就立刻停下，什么都别做**，告诉用户：

> `/automode` 和 plan 模式冲突，请按 Shift+Tab 退出 plan 模式后重新打 `/automode`。

原因：plan 模式禁止写操作，planner 写不了规划文件；plan 模式的指令优先级又高于本命令，结果是主会话自己用 opus 把规划做了，fable 完全不参与（09-08 实测：7 次 Agent 调用里 0 次 planner）。`/automode` 的阶段 2 本身就是批准环节，是 plan 模式的替代品，两者叠加只会互相干扰。

## 阶段 0：开工前

### 记下开工时间

第一步跑 `date +%s`，把结果写进第一条 `TaskCreate` 的标题（如「/automode 开工 1760000000：给列表加分页」）。之后每次 `automode-check --from` 用它，不用估分钟数。

### 先看有没有上一轮的残留（S1）

项目根有 `.automode-plan.md`、`.automode-handoff-*.md` 或 `.automode-plan-redesign.md` → **停下来问用户**：接着上次做，还是丢弃重来。（有 `.automode-plan-redesign.md` = 上次 Fable 重新规划完、还没并进原规划就中断了，接着做时先按阶段 2 的替换规矩把它并进去。）**不许不问就删**——进程崩溃后，这是唯一能恢复进度的东西（本机内存超规格，会随机崩进程）。

- **接着做**：跳过阶段 1。`.automode-plan.md` 若只是指向 `PLAN-*.md` 的短记录，以它写的那份规划、那几节为基准，连同它下面的修订补充。读规划第 3 节——每个问题下有 `✅ 用户答复` 标记的是上一轮答过的；**没有标记的照阶段 2 问**，不许当成已拍板（答复怎么写进规划，见阶段 2「本会话没有可续的 planner」）。然后看做到了哪一步：
  - 有比 `.automode-plan.md` **更新**的 `code-review-*.md` → 审查已经做过。读报告末尾「用户在 S4 的选择」和各轮复审结论，从阶段 4 的「修复」接着做，不重审、不重问已答的 🟡
  - 否则读每份 handoff（P7 要求每步记一行），列出「已完成 / 剩余」给用户看，从阶段 3 继续
  - **某个包没有 handoff**（还没做完第一步就崩了，或老版本流程）→ 判断它做到哪：git 仓库用 `git status` / `git diff` 对照规划里每步的文件清单；**不是 git 仓库就读相关代码**，对照规划逐步判断。读码量大就派 sonnet 子代理去核，别在主会话里大段读
  - 派接手的子代理时告诉它：**工作区里可能有上次没做完的改动，先核对再续，别重复改**
- **丢弃**：删掉这些文件，按新任务走

### 判断规模

任务明显很小（改 typo、调常量、单行修改、纯查询）→ 自己直接做，做完**仍走阶段 4 审查**。拿不准就走完整流程——规划的成本远低于返工。

### 核实际状态

任务描述、交接文档或 PLAN 里标着「待实施」的项，**动手前先用 `git log` / grep 核一遍是不是早就做完了**。计划文档常被实测证伪（09-18 一天里两项标着「待实施」的其实早已提交），照文档派活会白跑一整轮。不管走不走 planner 都要核。

### 用户中途追加需求

这个会话不是封闭的，随时欢迎补充。要分清「现在做」还是「下一轮做」，判据是**共不共用上下文**：

- **同任务的**（追问、补充、纠正、本轮改出的 bug、审查问题、对本轮产出的意见）→ 当场做
- **不相关的新任务**（新功能、另一个模块的 bug）→ 默认留到下一轮：
  1. 接住它，追问清楚，该确认的当场确认
  2. 用 **Edit** 追加进交接文档**末尾**的「下一轮待办」，连同问清的细节（这是使用方定的做法）
  3. `TaskCreate` 记一条「阶段 4.5：交接文档末尾已有新需求 ×N，保留」
  4. 告诉用户已记下，回到本轮任务
- **拿不准算哪一类，就当场做**——把该做的事推到下一轮，比多花点 token 糟得多（例：实现中用户说「顺便把列表改成倒序」，同一个页面，当场做）
- **用户说「现在就做」就做**，不拦、不劝、不重复解释成本

> 为什么默认往后放：新任务在本会话开工，就全程背着前一个任务的上下文，每次交互都更贵。实测一个会话追加了 2 个新需求，上下文从 140k 涨到 419k，单会话烧掉 21.90M 等效 token。

## 阶段 1：规划（fable）

### 什么时候不启动 planner

- 阶段 0 选了「接着做」
- 已有用户拍过板、细到能直接落地的规划（例：上一轮逐条确认过的 `PLAN-*.md`）。「拍过板」要有**白纸黑字的证据**：用户本轮亲口说的，或规划 / 交接文档里明写「已拍板、不用再问」。拿不准就不算。跳过时在回复里说明理由，实现子代理的 P1 点名读那份规划的哪一节。重跑 fable 只会产出一份更差的重复品，而它是流程里最贵的一环（单次约 2M）。**这种情况主会话先写一个很短的 `<项目根>/.automode-plan.md`**：「本轮规划 = `<PLAN 路径>` 第 x–y 节（拍板证据：……）；修订补充见下」——崩溃后续跑靠它找到基准规划，handoff 里的「步骤 N」也才有据可查

两种情况下**阶段 4 的审查一次都不能省**。

### 本会话已有一个相关的 planner → 用 SendMessage 复用

同一模块、同一阶段的后续、基于上一轮结果的修复 → **发回那个 planner，不要新起**（它已读过的代码和想清楚的约束全在）。上一轮的规划文件可能已在阶段 5 删掉，所以消息要写明这是新任务：

> 这是一个**新任务**，不是对待确认问题的回复。请按首轮规则把完整规划 Write 到 `<绝对路径>`，返回完整全文和待确认问题。任务：……

新任务跟旧规划确实无关，才新起（仍守下一节「一次只开一个」）。

### 规划一次只开一个

同一时间只跑**一个** `planner-fable`。多个任务、或规划途中用户又加了需求，都交给同一个 planner 一起规划，不另起第二个：

- 还没启动：几个任务写进同一个 prompt，规划文件里按任务分节
- 正在跑或刚返回：`SendMessage` 把新需求发给它——「这是追加需求，请并进同一份规划（新增步骤编 3a、3b 或追加在最后，不挪号），返回更新后的全文和新增的待确认问题」

> 10-21 两个 fable 规划并行，撞了两次 `429 Concurrency limit`；失败的请求网关照样计费，两周累计约 43 次、$40。实现类子代理不受这条限制，仍按【派活规矩·并行】最多 2 个。

### 新起 planner

用 Agent 工具启动 `planner-fable`，**不传 model 参数**。直接启动，不要先开 Explore。prompt 里给足它查不到的东西：

- 项目的**绝对路径**，规划文件的绝对路径（一般是 `<项目根>/.automode-plan.md`）
- 已讨论的约束、已排除的方案、用户的偏好、用户在本轮说过的原话
- 已知相关文件在哪就直接点名

**几分钟不涨 token 是正常的**：fable 的思考是加密的，usage 要等整条响应完成才写入，实测空窗最长近 5 分钟。想确认它在干活，看 `~/.claude/projects/<项目>/<会话>/subagents/agent-*.jsonl` 的修改时间，几十秒内动过就是在跑。**别当成卡死重开**。

### planner 返回后

1. **跑一次 `automode-check --from <开工时间戳>`**，确认规划实际跑在 fable 上。出 ❌ → 停点 S7
2. **规划全文原样贴进对话，一字不减**，连同它附的摘要、分步概览、待确认问题。用户要在对话框里直接 review，这是他明确要求的。不要压缩、不要只列要点、不要说「详见文件」
3. **不要自己再把规划写一遍文件**——planner 已经写好了，重写等于同样内容在贵模型上生成两遍

## 阶段 2：待确认问题（S2）

规划第 3 节「待确认问题」**只要不是空的，就按【决策权】的问法交给用户，等他答完再往下走**。

- 规划第 5 节「已自行决定」是 planner 自己定的小事，用户在全文里能看到。他对其中哪条有异议，同样转发给 planner 改
- 用户答完 → `SendMessage` 发回**同一个** planner（有可续的就绝不新起，新起的丢掉全部上下文）：「用户对待确认问题的答复：Q1 选……；Q2 选……。请按修订规则更新规划文件。」
- **本会话没有可续的 planner**（阶段 0 选了接着做、或直接用了用户的 `PLAN-*.md`），规划又要按用户的答复 / 决定改 → 按改动量选做法。目标是**一处都不丢、所有人读到的是同一个版本**，同时别为几行改动花一整份 fable：
  - **改动少**（一两处，不牵动其它步骤、不改文件清单和接口）→ 主会话把决定写进 `<项目根>/.automode-plan.md` 的「修订补充」，每条写清：原规划哪一节 → 改成什么 → 用户在哪个停点定的。续跑时 `.automode-plan.md` 本身就是规划，就直接改受影响的那几行并标 `✅ 用户答复`。之后实现子代理（P1）和审查员都拿到原规划 + 修订补充，注明冲突处以修订为准
  - **改动多**（牵动多个步骤，或改了文件清单、接口，包括推翻核心方案）→ **先问用户怎么改**（和 S2 / S3 的问题放进同一次 `AskUserQuestion`，你标出推荐项）：
    - **A 整份改**（快、省）：派 sonnet 子代理按决定清单改，prompt 带 P2 和**下面整段替换规矩**（只改涉及的节或步骤、不挪号、补 ✅）——不交给它，它会按习惯顺延编号或顺手整理别的节。改动集中时也可以主会话直接改
    - **B fable 重新规划**（约 2M，适合要重新设计的情况）：新起 `planner-fable`（不传 model），消息写「这是基于已有规划的重新规划：先 Read `<原规划路径>`，按下列用户决定重新设计第 x–y 步，写进 `<项目根>/.automode-plan-redesign.md`（**不要写 `.automode-plan.md`，也不要写原规划**），返回全文」。它返回后照阶段 1–2 贴全文、问新的待确认问题，再按下面的替换规矩并进原规划，核对完删掉 `.automode-plan-redesign.md`
      > 为什么单独一个文件：`.automode-plan.md` 有时就是原规划本身（续跑时），有时装着指向 `PLAN-*.md` 的记录和还没并回去的修订补充。planner 按首轮规则是整份 Write，写进去就把这些全覆盖了
    - **选哪个是用户的决定**，不许你按「看起来改动不大 / 很大」自己挑
  - **替换规矩**（A、B 都适用，目标是一处都不丢）：
    - **先备份，再派 A 或 B**：原规划不在 git 里、或有未提交改动时，派活**之前**先复制一份 `<原名>.bak-<YYYYMMDD-HHMM>`（续跑时原规划就是 `.automode-plan.md`，同样要备）。同名备份已存在就不覆盖——要留的是最早那份原始内容
    - **只替换本轮涉及的节或步骤**，原规划里其它内容原样保留——用户自己的 `PLAN-*.md` 常是多阶段文档，本轮之外的节还被别的文档引用
    - **替换后核对**：diff 确认只有预期的节变了（git 里用 `git diff`，不在 git 里就和备份比）；逐条核对每个用户决定都已落进文件
    - **保留已有步骤编号**：新增的编 3a、3b 或追加在最后，删掉的标「已取消」，**不挪号**——handoff 和并行的包按编号记进度，挪号会让人把做完的步骤再做一遍、跳过新步骤
    - 已答的问题补 `✅ 用户答复`
    - 有包正在并行实现时，等它收工（或暂停）后再替换，替换后告诉接手的子代理哪几步变了
  - 不管哪种，**都不许只把答复写进实现子代理的 prompt**——审查员和下一轮读的是规划文件，答复没进文件，迟早会被当成「和规划不符」改回去
- planner 会在规划第 3 节已答的问题下标 `✅ 用户答复`（中断后靠它判断哪些问过）。它的修订回复包含三样：改了哪几处、**受影响步骤的新文件清单**、**新增的待确认问题**（没有就写「无」）。**原样贴给用户**
  - 有新增问题 → 回到本阶段再问
  - 之后判断并行，以修订后的文件清单为准，不用上下文里的旧版

## 阶段 3：实现（sonnet，最多并行 2 个）

### 开工先报分母

按规划 §2 的步骤用 `TaskCreate` 建任务列表，再用一句话报：「本轮共 N 件：……，其中 X 件只能你做（凭据 / 要你点头的决定）」。使用方最大的痛点是不知道做到哪、还差多少。

### 切包、派活

- 按【派活规矩】切成每包 1–3 个步骤，prompt 带 **P1–P9 全部九条**，Agent 传 `model: "sonnet"`
- 并行按【派活规矩·并行】判断，拿不准就串行

### 文档类步骤留到阶段 4.5

规划里标了 **[文档]** 的步骤（ADR、交接文档、下一阶段计划、README、CHANGELOG、验收用例表、使用说明）**一律跳过**，先把代码步骤全做完直接进阶段 4。直接用 `PLAN-*.md` 时，这类节通常排在末尾（`§14`、`§15`），按编号顺序做就会落在审查之前——这是错的。

> 为什么：审查必然会改代码，改完文档就过时了。实测一轮里同一批文档写了两遍（0.47M + 0.79M）。

**跳过时当场记下清单**：`TaskCreate` 建一条「阶段 4.5 文档收尾：§2 步骤 7、8」。中间隔着审查、修复、复审，跨度一两个小时，不记必忘。

**例外**：本轮任务本身就是写文档（没有代码改动），文档就是产出物，正常做。

### 子代理返回后

- 跑 `automode-check --from <开工时间戳>`，出 ❌ → 停点 S7。第一个包就核：忘了传 model 跑成 opus 的话，后面的包会照样重复
- 跑验证命令，看结果
- 它报「已清理 / 已还原 / 无残留」→ **自己核**：grep 那个具体的修改点，查它可能漏掉的其它残留位置（数据库关联表、生成的目录）。别拿 `git diff` 总行数当证据，那个文件可能被好几个包改过
- 按 P7 收工了 → 新起一个接力；被限流打断 → SendMessage 续（见【派活规矩·中断】）
- 报了缺凭据 / 缺前提（S5）→ 问用户要。不许自己绕，也不许记成「未验证」就往下走

### 方向性分歧（S3）

**什么算**：子代理要改变规划里的方案、接口、数据结构、文件范围，或推翻用户在阶段 2 的答案；或者它报告规划的做法走不通（P9）。它已经自作主张改了、只在报告里带一句的，同样算。

**怎么办**：停下来，用 `AskUserQuestion` 交给用户，给出「规划原文 / 子代理的提议 / 各自的后果」→ 用户定了之后，把决定写进规划（本会话有 planner 就 `SendMessage` 让它改；没有就按阶段 2「本会话没有可续的 planner」按改动量处理）→ 再按修订后的规划派活。已经被自作主张改掉的部分，按用户的决定保留或返工。

## 阶段 4：审查与修复（opus）

实现完**自动**启动 `code-reviewer`（不传 model），不问用户要不要审。

界面小改（主会话按【主会话分工】直接改的那类）**攒批审**：不为一处单独起审查，攒着和下一批改动一起审；最晚在给用户提交脚本或定档之前审一次。本轮只有这类小改时，审查范围就是这几处。审还是要审——10-19 一批小改审了 $10，查出的「手机上按钮撑出横向滚动」就是样式改动引起的。

### 启动时一次给足四样

审查慢，多半是它在自己摸索「改了什么」和「本该是什么样」。这两件事你都知道，直接告诉它：

1. **改动范围**：git 仓库给 `git diff`，否则逐个列文件。能精确到函数名或行号区间就给
2. **规划文件路径**：让它知道设计意图，否则会把「规划要求的做法」误报成缺陷。这条对减少误报作用最大。有「修订补充」时**两份都给**，注明冲突处以修订补充为准、那是用户的决定——不然审查员会把用户改过的地方报成「与规划不符」的 🔴，被直接修回去
3. **本轮明确不管的部分**：只放规划或用户明确延后的。**别放自己没验证过的推断**（「这个分支不可达」「这是死代码」）——那等于给审查造盲区。09-07 就有一条「不可达」被审查证伪，反例正是同一轮新写的测试
4. **实现子代理已经自查过什么**：跑了哪些测试、验证过哪些边界

范围聚焦本次改动是为了让它专注，不是为了省时间；改动周围的代码和调用方必须一起看，接缝处才是 bug 高发区。**绝不为了快而压缩审查**——前面省下的时间就是留给这里的。

### 拿到结果：先核模型，再落盘，再完整列出

1. 跑 `automode-check --from <开工时间戳>`，确认审查跑在 opus 上。出 ❌ → 停点 S7，别在一份跑错模型的审查上继续修
2. **写成文件** `<项目根>/code-review-<YYYYMMDD-HHMM>.md`（审查员不能写文件，由你写）
3. **在终端用表格完整列出，一条都不许省**：

   | 编号 | 严重度 | 位置 | 问题 | 触发场景 | 建议 |
   |---|---|---|---|---|---|
   | R1 | 🔴 | `src/a.ts:42` | 具体缺陷 | 什么输入 / 状态导致什么错误结果 | 怎么改 |

   「触发场景」不许空或含糊，它是判断真伪的唯一依据。只报数量和严重度等于什么都没说。

### 先把 🟡 交给用户（S4）

表格之后写你对每条 🟡 的判断（该修 / 可以不修 / 为什么），再用 `AskUserQuestion` 让用户选修哪些。🔵 一句带过，用户也可以点名要修。**不许因为「改动小」「显然该修」就自己动 🟡。**

用户答完，把他的选择**追加到审查报告末尾**的「用户在 S4 的选择」（修哪些、不修哪些）。中途崩了，续跑靠它接上，不用再问一遍。

### 修复：一批修完，复审一次

1. 🔴（必修）+ 用户批准的 🟡（+ 他点名的 🔵）**一起**派修复子代理：`model: "sonnet"`，prompt 给审查报告路径和要修的编号，带 P1–P9。派完、结束回合等它们时，按【主会话分工】看要不要附压缩命令
2. 修完 `SendMessage` 发回**同一个** `code-reviewer`：「已按 R1、R3 修改（改了 `文件:行`……），请复审」
3. 复审的新发现编 **N1、N2…**。**每一轮复审结果都追加进同一份 `code-review-*.md`**——阶段 4.5 的文档子代理只能读文件（09-10 就因收口轮结论没落盘，文档里少了一条）。追加完，之后第一次结束回合时同样按【主会话分工】看要不要附压缩命令
4. 复审出新的 🔴 → 直接修，再复审；新的 🟡 → 照样先问用户
5. **两轮后仍有 🔴（S6）** → 停下来如实说卡在哪，不要无限循环

审查结束后，因为用户提意见又改的代码，同样送同一个 `code-reviewer` 复审。

审查员被 429 / 503 打断 → `SendMessage` 续同一个（实测重开一次多花 1.17M，还会漏掉追到一半的线索）。

### 用户说「超过 N 分钟就留到下一轮」

这是**延期，不是砍范围**，一条都不删。被问耗时给实测数字和依据，别为了让他同意往低了报。

- 用户明确说要修的 → 标「已拍板、下一轮必修」
- 用户还没表态的 🟡 → 标「**待用户决定（🟡）**」，下一轮照样问。**不许标成已拍板**——那会变成下一轮跳过提问的「证据」
- 留档要能独立看懂：每条的位置、触发场景、改法整段抄进交接文档。只留审查报告路径不够，它可能被 `.gitignore` 排除

## 阶段 4.5：文档收尾（审查和修复都结束后）

代码定稿了，才写阶段 3 跳过的文档。派 `model: "sonnet"` 的文档子代理，prompt 带 P1–P9 中适用的几条（至少 P2、P5、P6、P7），并给足：

1. 跳过的文档步骤清单（阶段 3 记下的那条）
2. **审查报告路径** + 修掉了哪几条（R×、N×）——文档描述的是**修复后**的最终状态
3. 判定不修的 🟡🔵、以及用户决定先写文档时仍未修的 🔴 → 作为已知问题写进交接文档；用户还没表态的 → 标「待用户决定」
4. **交接文档末尾已有的新需求**（阶段 0 写进去的）→ 告诉它**保留原样，不要重写那几条**
5. **`.automode-plan.md` 里对 `PLAN-*.md` 的修订补充**（如有）→ 并进原规划的对应节（或项目的交接文档 / 下一阶段计划），让下一轮读到的规划和代码一致

派活前核一遍：prompt 里每一处「以 X 文件为准」，X 里**真的**有那些内容。文档子代理报「某条找不到」→ 先查自己给的源文件漏没漏，补上后 `SendMessage` 让它接着写。它宁可交白也不编，这种行为要在汇报里明确肯定——它是挡住幻觉进文档的最后一道闸。

文档写完后代码不该再动。如果还要改，改完送审查复审，再同步文档——**对不上的交接文档比没有更坏**。

## 阶段 5：清理

- 确认全部完成后，删 `.automode-plan.md`、`.automode-plan-redesign.md`（如果还在）和已完成包的 `.automode-handoff-*.md`。规划备份 `*.bak-<时间>` **不删**，汇报里列出路径。`.automode-plan.md` 若装着对 `PLAN-*.md` 的修订补充，删之前先 grep 核实每条都已并进去（阶段 4.5 第 5 条）
- 还有没做完的包 → 先把剩余事项抄进交接文档，告诉用户，再删
- `code-review-*.md` **保留**，提示可加进 `.gitignore`
- **不 commit、不 push**

## 最后汇报

1. **做了什么**：改了哪些文件
2. **决定清单**：每个决定 + 谁定的（用户在阶段 X 答的 / planner 第 5 节写明的 / 用户亲口授权的）。没有「编排者自己定的」这一类；真有，标出来并说明
