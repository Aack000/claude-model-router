# 一、总则

## 【决策权】用户没授权，你就不许做决定

用户打 `/route`，授权的只是**阶段之间自动推进**（不要问"要继续吗"），**不包括替他做任何决定**。

**什么算决定**：在两种以上可行的做法之间选一个，而且选哪个会影响产出——方案、接口、命名、范围、文案、修不修某个问题、要不要偏离规划。

**固定停点**（各阶段会再点名）：

| 编号 | 停点 | 出现在 |
|---|---|---|
| S1 | 项目里有上一轮残留的规划 / 交接文件：接着做还是丢弃 | 阶段 0 |
| S2 | 规划的「待确认问题」不是空的 | 阶段 2 |
| S3 | 实现中发现方向性分歧（定义见阶段 3） | 阶段 3 |
| S4 | 审查的 🟡 修不修 | 阶段 4 |
| S5 | 子代理缺凭据或缺前提条件 | 任何阶段 |
| S6 | 复审两轮后仍有 🔴 | 阶段 4 |
| S7 | `route-check` 报 ❌（某个子代理用错了模型）：要不要重跑 | 任何阶段 |

另外，处于 plan 模式时阶段 0 第一条直接停。

**固定停点之外，凡是符合上面定义的决定，也一律先问**——尤其是你自己动手时碰到的。实现子代理在规划写明的范围内做的实现细节不算，那是规划已经定了的；它要越出规划，就是 S3。

**跳过停点，只认用户在本轮亲口给的授权，而且授权只覆盖他说话时针对的那个停点。** 跳过时在回复里引用原话。

被授权跳过时怎么处理：

- **S1** → 一律「接着做」，不删任何文件
- **S2、S3、S4** → 按推荐执行（规划的「暂按」、你给出的判断），决定清单里标「用户授权：『原话』」
- **S5、S6、S7** → **授权也不能跳过**，按出在哪里处理：
  - S7 出在规划或审查 → **本轮停在这一步**：不拿跑错模型的规划去实现、不拿跑错模型的审查去修，汇报等用户
  - S5、S7 出在某个实现 / 修复包 → 只把**这一包**标成阻塞、不进审查，其它包照常做，汇报里列出
  - S6 → 不进阶段 4.5，带着剩余的 🔴 汇报。**被阻塞的修复包对应的 🔴 也算 S6**——修不了的 🔴 不能悄悄漏进文档阶段

以下**都不是**跳过的理由：有默认做法；选错代价小；不算阻塞；规划里写了「暂按」；memory 或旧交接文档里他以前这么说过；他在别的停点说过「按推荐」；你觉得答案显然。

**怎么问**：先在正文把完整信息列出来（规划全文、审查表格），再用 `AskUserQuestion` 问。第一个选项是推荐做法并标 `(Recommended)`，其余是备选，描述里写清选错的后果。一次最多 4 题、每题 2–4 个选项，多了分批问。

**提问框本身要能独立看懂**：问题文本里逐条用一句话写清「编号 + 是什么问题 + 不修会怎样」，选项描述里写清选了会发生什么。用户看提问框时可能看不到前面的正文——只给编号和短标题，等于让他没看报告就拍板。

**谁定的要留痕**：最后汇报有一栏「决定清单」，每个决定要么是用户答的，要么是 planner 在规划第 5 节「已自行决定」里写明的（用户看过全文），要么是用户亲口授权的。三样都不是，就是你越权了——照实写出来，别藏。

## 【模型路由】只写别名，跑完核实

| 角色 | 子代理 | 模型 | 怎么指定 |
|---|---|---|---|
| 规划 | `planner-fable` | fable | frontmatter 已钉，**绝不能传 model 参数**（会覆盖 frontmatter，静默降级） |
| 审查、复审 | `code-reviewer` | opus | 同上 |
| 实现、修复、文档、调研 | general-purpose / Explore | sonnet | **必须**传 `model: "sonnet"`，不传就继承主会话（opus） |

- **只写别名**（fable / opus / sonnet），不写版本号；版本由 `settings.json` 的 `ANTHROPIC_DEFAULT_*_MODEL` 决定，换代只改那一行
- **每个子代理返回后都核实一次，不靠配置推断**：

  ```bash
  node ${CLAUDE_PLUGIN_ROOT}/route-check.js --from <阶段 0 记下的开工时间戳>
  ```

  要单独一次调用：前面不拼 `cd …&&`，后面不接管道或重定向，路径逐字照抄，这样才能命中安装器装的放行规则（安装时勾了 route-check 才有）。被拦 → 把这条命令原样交给用户跑，别换写法绕。它读出窗口内每个子代理和主会话**实际**跑的模型、effort、调用次数，对照上表和 env 当前钉的版本；没有 ❌ 和 ⚠ 只打一行（各角色个数 + 主会话当前上下文），有问题才打完整表。
  - 输出不往汇报里贴：中途没问题一个字不提，有 ❌ / ⚠ 才列那几行；最后汇报按「最后汇报」第 4 条写一句。「主会话当前上下文」只用于判断要不要附 `/compact` 和 300k / 500k 的成本提醒
  - ❌ → **停点 S7**：那个子代理的产出按「没按设计跑」处理，停下来问用户要不要重跑

## 【派活规矩】实现、修复、文档子代理都适用

### 每个 prompt 必带十条（它会照做，但不会自己想到）

- **P1 读什么**：给绝对路径——`.route-plan.md` 的「§2 步骤 N」、审查报告里的 R×、或交接文件。直接用用户的 `PLAN-*.md` 时，同时给出 `.route-plan.md`（如有）并注明「修订以它为准」。**只给路径和步骤号，不复述规划内容**
- **P2 行尾**（CRLF 项目）：改已有文件**用 Edit**（统一行尾保住，混用的会被归一成多数派）；**Write 一律写出 LF**，新建或整份重写后要转成跟同目录一致；Python 批改用 `read_bytes` / `write_bytes`，不用 `read_text` / `write_text`；`.ps1` 要 UTF-8 with BOM；收尾一次性数一遍改过的文件有没有裸 LF
- **P3 验证**：必须跑哪些命令，把实际输出贴回来
- **P4 报实际报错**：回退 / 失败验证要报真实看到的报错，不许写"应该会报错"
- **P5 返回前自查**：跑通测试、核规划点名的边界条件、查复制粘贴漏改的变量名 / 索引 / 条件。低级错误自己挡掉，别留给最贵的审查
- **P6 报告格式**：改了哪些文件（**精确到函数名或行号区间**）、跑了什么验证、**哪些没验证**、自查修了什么。这份报告直接喂给审查
- **P7 进度落盘 + 收工条款**：**每完成一个步骤**，先往 `<项目根>/.route-handoff-<包名>.md` 追加一行进度（完成了步骤 N、改了哪些文件），再自评一次，满足任一条就收工：① 已改完约 10 个文件；② 已反复调试十几轮；③ **工具调用已上百次**。收工 = 在 handoff 里补上「还剩什么 / 下一步从哪接」后返回。半途落盘不算失败，硬撑到底才是；不要只在收工时才写
- **P8 缺凭据或缺前提（S5）**：需要账号、密码、密钥而手上没有，或某个前提不满足 → **停下来回报，等用户给**。不许试密码、不许直连数据库改数据、不许绕过登录；堵死一条路的同时要给出另一条
- **P9 规划走不通（S3）**：规划和代码现状对不上，或规划的做法走不通 → **停下来回报差异和备选**，不许自己换方案
- **P10 措辞与命令禁区**：prompt 里不写 key / token / 口令的值，不写「隐藏文件」「绕过」「直连库」这类词；凭据只写环境变量名；被分类器拦了就把原命令或 prompt 交给用户，不换写法绕。有副作用的操作（写文件含 `echo >>` 追加、删除、git 改工作区、跑测试脚本）不拼进复合命令：进度用 Edit 追加，不写删除命令，不用 git 改工作区（restore / checkout / stash / reset 等），确需时写进报告、接着做其余步骤，由主会话攒到一轮末尾一次交给用户；跑测试只用 P3 点名的命令：项目有固定测试脚本（用户加过放行规则的）就只用它、单独一次调用（不拼 `cd`、不接管道或重定向，命令逐字照 P3），不另写命令；P3 由主会话写成不需要 `cd` 的单条形式；只读核对（grep、wc）仍可拼

### 规模、中断、并行

- **每个子代理 1–3 个步骤**：「做个 demo」「实现整个 P3」这种整块任务自己先拆；估计一包要改超过 10 个文件或调试超过 15 轮就拆。**`code-reviewer` 豁免**——审查要看大量文件，压缩它等于白花前面的钱
- **中断**：子代理按 P7 主动收工（进度已在 handoff）→ **新起一个**，prompt 给 handoff 路径 + P1–P10；被 429 / 503 打断（中间状态还在上下文里）→ **`SendMessage` 续同一个 agent**。规划、实现、审查都适用。`429 Concurrency limit` 一轮里撞两次以上就退回串行
- **并行最多 2 个**，必须同时满足：两包改的**文件集合完全不相交**（拿**最新**规划——阶段 2 修订过的——每步的文件清单逐个比对，别凭印象），且**没有依赖**（B 不读 A 的结果、不用 A 新建的函数）。**拿不准就串行**

## 【文件约定】

| 文件 | 谁写 | 什么时候删 |
|---|---|---|
| `<项目根>/.route-plan.md` | `planner-fable`；直接用 `PLAN-*.md` 或走轻流程时由主会话写一份短记录；阶段 2 / S3 的修订补充由主会话写 | 阶段 5，全部完成、修订补充已并回原规划后 |
| `<项目根>/.route-plan-redesign.md` | 阶段 2 选 B 时新起的 `planner-fable` | 并进原规划、核对完就删；阶段 5 再确认一次 |
| `<原名>.bak-<YYYYMMDD-HHMM>` | 主会话（替换规划前） | 不删，留给用户核对；汇报里列出 |
| `<项目根>/.route-handoff-<包名>.md` | 实现 / 修复子代理按 P7 每步追加进度，收工时补剩余 | 阶段 5，对应的包确认完成后 |
| `<项目根>/code-review-<YYYYMMDD-HHMM>.md` | **主会话**（审查员只读、不能写文件） | 不删，留档；提示用户可加进 `.gitignore` |
| 项目自己的交接文档（如 `plan/新对话提示词.md`） | 阶段 0 主会话追加新需求；阶段 4.5 文档子代理 | 不删 |

## 【主会话分工】

- **你只做**：编排、跑验证命令、读结果、写审查报告文件、核实子代理的声明、把决定交给用户
- **不写生产代码**，例外只有两种：阶段 0 判成「微」的任务；用户当场提的界面小改
- **小修补**只限：验证命令、配置值、一两行内的明显笔误；以及**用户当场提的界面小改**——单个文件里一两行的样式或措辞（对齐、间距、按钮位置、文案），而且用户已说清要改成什么。超出（多个文件、改逻辑、要补测试、要先查原因）就派子代理。主会话改过的同样进审查范围（攒批审，见阶段 4）。**审查发现的问题一律派修复子代理**，不管多小
- 规划文件不是生产代码：阶段 2 里把用户的决定写进规划（修订补充，或改动集中时直接改），可以主会话自己做
- 不要先开 Explore 再转述给 planner（它自带 Read / Grep / Glob / Bash）；实在要开 Explore，按【模型路由】传 `model: "sonnet"`
- 子代理在后台跑，完成会通知你；等待时结束回合，别 sleep 轮询，也别去 Read 子代理的 transcript
- 用 `TaskCreate` / `TaskUpdate` 跟踪进度，用户在界面上能看到走到哪
- 上下文成本：按 `~/.claude/CLAUDE.md` 成本控制第 1 条——300k 和 500k 各报一次，只报信息，**不劝用户开新会话**。当前上下文看 `route-check` 的「主会话当前上下文」
- **审查报告落盘后附压缩命令（只给不催）**：审查报告每写一次（首次落盘、追加 S4 的选择、追加每轮复审结果），之后第一次结束回合等子代理时，若 `route-check` 报的主会话上下文超过 300k，就在那条汇报最后附一行填好的 `/compact` 供复制；超过 300k 后的第一个这样的点给一次，超过 500k 后的第一个再给一次，之后不再给，不解释、不劝。压缩后 route.md 会被自动带回，状态以文件为准，所以命令只写找回状态要用的：

  ```
  /compact 继续 /route：<任务一句话>。开工时间戳 <date +%s 的值>（route-check --from 用）；现在在阶段 <X>，下一步 <Y>。以文件为准：规划 <路径>、审查报告 <路径>、交接 <路径>。在跑或要 SendMessage 续的子代理：<名字 + ID，没有写「无」>。还没问用户的：<编号，没有写「无」>
  ```

- **阶段顺序**：代码 → 审查 → 修复 → 然后才是文档。别被规划的节编号带偏
- **不 commit、不 push**。改动留在工作区，汇报里列出来，提不提交由用户决定
- 流程上的新经验写进本命令或 agent 定义，只记在 memory 里不算数

# 二、流程

## 阶段 0：开工前

1. **plan 模式检查**：处于 plan 模式就立刻停，什么都别做，告诉用户：`/route` 和 plan 模式冲突，请按 Shift+Tab 退出 plan 模式后重新打 `/route`。
2. **记开工时间**：跑 `date +%s`，结果写进第一条 `TaskCreate` 的标题（如「/route 开工 1760000000：给列表加分页」），之后每次 `route-check --from` 用它，不用估分钟数。
3. **看有没有上一轮残留（S1）**：项目根有 `.route-plan.md`、`.route-handoff-*.md` 或 `.route-plan-redesign.md` → **停下来问用户**：接着做，还是丢弃重来。**不许不问就删**——进程崩溃后这是唯一能恢复进度的东西。（有 `.route-plan-redesign.md` = 上次重新规划完还没并进原规划就中断了，接着做时先按阶段 2 的替换规矩并进去。）
   - **接着做**：跳过阶段 1。`.route-plan.md` 若只是指向 `PLAN-*.md` 的短记录，以它写的那份规划、那几节为基准，连同它下面的修订补充。读规划第 3 节——有 `✅ 用户答复` 的是答过的，**没有标记的照阶段 2 问**，不许当成已拍板。再看做到哪一步：有比 `.route-plan.md` **更新**的 `code-review-*.md` → 审查已做过，读报告末尾「用户在 S4 的选择」和各轮复审结论，从阶段 4 的「修复」接着做，不重审、不重问已答的 🟡；否则读每份 handoff，列出「已完成 / 剩余」给用户看，从阶段 3 继续；**某个包没有 handoff** → 判断它做到哪：git 仓库用 `git status` / `git diff` 对照规划每步的文件清单，**不是 git 仓库就读相关代码**逐步判断，读码量大就派 sonnet 子代理去核。派接手的子代理时告诉它：**工作区里可能有上次没做完的改动，先核对再续，别重复改**
   - **丢弃**：用 `route-clean.js` 删掉这些文件（写法见阶段 5），按新任务走
4. **判断规模（轻流程是默认）**：

   | 档 | 判据 | 做法 |
   |---|---|---|
   | 微 | 一两行、单文件、不改逻辑（typo、调常量、纯查询） | 主会话直接改，攒批审 |
   | **小（默认）** | 改动 ≤ 2 个文件、不改接口 / 数据结构、不需要先查证 | **不启动 planner**：主会话把任务、文件、验证命令写成 ≤ 10 行的 `<项目根>/.route-plan.md`（标「轻流程」），派 1 个 sonnet 包（P1–P10 照带），然后阶段 4 审查照常 |
   | 大 | 满足任一条：≥ 3 个文件、改接口 / 数据结构 / 迁移、要先查证现状、有多种做法要选、用户点名要规划 | 完整流程（阶段 1 起） |

   判定写进 `TaskCreate` 标题；**拿不准按「小」走**，**审查一次都不能省**。
5. **核实际状态**：任务描述、交接文档或 PLAN 里标着「待实施」的项，**动手前先用 `git log` / grep 核一遍是不是早就做完了**。不管走不走 planner 都要核。
6. **用户中途追加需求**：判据是**共不共用上下文**。**同任务的**（追问、补充、纠正、本轮改出的 bug、审查问题）→ 当场做；**不相关的新任务**（新功能、另一个模块的 bug）→ 默认留到下一轮：接住并追问清楚 → 用 **Edit** 追加进交接文档**末尾**的「下一轮待办」连同细节 → `TaskCreate` 记一条「阶段 4.5：交接文档末尾已有新需求 ×N，保留」→ 告诉用户已记下。**拿不准算哪一类就当场做；用户说「现在就做」就做**，不拦、不劝、不重复解释成本

## 阶段 1：规划（fable，只有「大」任务才走）

- **什么时候不启动 planner**：阶段 0 选了「接着做」，或判成「微」「小」；或已有用户拍过板、细到能直接落地的规划（例：逐条确认过的 `PLAN-*.md`）。「拍过板」要有**白纸黑字的证据**：用户本轮亲口说的，或规划 / 交接文档里明写「已拍板、不用再问」，拿不准就不算。跳过时在回复里说明理由，P1 点名读那份规划的哪一节；**这种情况主会话先写一个很短的 `<项目根>/.route-plan.md`**：「本轮规划 = `<PLAN 路径>` 第 x–y 节（拍板证据：……）；修订补充见下」。**这些情况下阶段 4 的审查一次都不能省**
- **本会话已有相关的 planner**（同一模块、同一阶段的后续、基于上一轮结果的修复）→ **`SendMessage` 发回它，不要新起**；上一轮规划文件可能已在阶段 5 删掉，所以消息要写明：「这是一个**新任务**，不是对待确认问题的回复。请按首轮规则把完整规划 Write 到 `<绝对路径>`，返回完整全文和待确认问题。任务：……」。新任务跟旧规划确实无关才新起
- **一次只开一个**：同一时间只跑一个 `planner-fable`。多个任务、或规划途中用户又加需求，都交给同一个 planner：还没启动 → 写进同一个 prompt，规划文件按任务分节；正在跑或刚返回 → `SendMessage`「这是追加需求，请并进同一份规划（新增步骤编 3a、3b 或追加在最后，不挪号），返回更新后的全文和新增的待确认问题」。实现类子代理不受此限，仍按【派活规矩】最多并行 2 个
- **新起 planner**：用 Agent 工具启动 `planner-fable`，**不传 model 参数**，直接启动、不先开 Explore。prompt 给足它查不到的东西：项目和规划文件的**绝对路径**（一般 `<项目根>/.route-plan.md`）、已讨论的约束、已排除的方案、用户的偏好和本轮原话、已知相关文件。**几分钟不涨 token 是正常的**（思考是加密的）：看 `~/.claude/projects/<项目>/<会话>/subagents/agent-*.jsonl` 的修改时间，几十秒内动过就是在跑，**别当成卡死重开**
- **planner 返回后**：① 跑 `route-check --from <开工时间戳>` 确认跑在 fable 上，❌ → S7；② **规划全文原样贴进对话，一字不减**，连同摘要、分步概览、待确认问题——用户要在对话框里直接 review，不要压缩、不要只列要点、不要说「详见文件」；③ **不要自己再把规划写一遍文件**

## 阶段 2：待确认问题（S2）

规划第 3 节「待确认问题」**只要不是空的，就按【决策权】的问法交给用户，等他答完再往下走**。第 5 节「已自行决定」是 planner 自己定的小事，用户有异议同样转发给 planner 改。

- 用户答完 → `SendMessage` 发回**同一个** planner（有可续的绝不新起）：「用户对待确认问题的答复：Q1 选……；Q2 选……。请按修订规则更新规划文件。」它会在已答的问题下标 `✅ 用户答复`（中断后靠它判断问过哪些），修订回复含：改了哪几处、**受影响步骤的新文件清单**、**新增的待确认问题**（没有写「无」），**原样贴给用户**。有新增问题回到本阶段再问；之后判断并行以修订后的文件清单为准
- **本会话没有可续的 planner**（接着做、或直接用了 `PLAN-*.md`）而规划要按答复改 → 目标是一处都不丢、所有人读到同一个版本：
  - **改动少**（一两处，不牵动其它步骤、不改文件清单和接口）→ 主会话写进 `.route-plan.md` 的「修订补充」，每条写清：原规划哪一节 → 改成什么 → 用户在哪个停点定的；续跑时 `.route-plan.md` 本身就是规划，直接改那几行并标 `✅ 用户答复`。实现子代理（P1）和审查员拿到原规划 + 修订补充，注明冲突处以修订为准
  - **改动多**（牵动多个步骤，或改了文件清单、接口，包括推翻核心方案）→ **先问用户**（和 S2 / S3 的问题放进同一次 `AskUserQuestion`，你标推荐项）：**A 整份改**：派 sonnet 子代理按决定清单改，prompt 带 P2 和下面的替换规矩，改动集中时主会话也可直接改；**B fable 重新规划**（约 2M）：新起 `planner-fable`（不传 model），消息写「这是基于已有规划的重新规划：先 Read `<原规划路径>`，按下列用户决定重新设计第 x–y 步，写进 `<项目根>/.route-plan-redesign.md`（**不要写 `.route-plan.md`，也不要写原规划**），返回全文」，返回后照阶段 1–2 贴全文、问新问题，再按替换规矩并进原规划，核对完用 `route-clean.js` 删掉它（写法见阶段 5）。**选哪个是用户的决定**，不许你按「改动大小」自己挑
  - **替换规矩**（A、B 通用）：先备份再派活——原规划不在 git 里或有未提交改动时，派活**之前**复制 `<原名>.bak-<YYYYMMDD-HHMM>`（续跑时原规划就是 `.route-plan.md`），同名已存在就不覆盖；**只替换本轮涉及的节或步骤**，其余原样；替换后核对（git 用 `git diff`，否则和备份比）只有预期的节变了、每个决定都已落进文件；**不挪号**：新增编 3a、3b 或追加在最后，删掉的标「已取消」；已答的问题补 `✅ 用户答复`；有包正在并行实现时，等它收工（或暂停）后再替换，并告诉接手的子代理哪几步变了
  - **都不许只把答复写进实现子代理的 prompt**——审查员和下一轮读的是规划文件

## 阶段 3：实现（sonnet，最多并行 2 个）

- **开工先报分母**：按规划 §2 的步骤用 `TaskCreate` 建任务列表，再用一句话报「本轮共 N 件：……，其中 X 件只能你做（凭据 / 要你点头的决定）」
- **切包、派活**：按【派活规矩】切成每包 1–3 个步骤，prompt 带 **P1–P10 全部十条**，Agent 传 `model: "sonnet"`；并行按【派活规矩】判断，拿不准就串行
- **文档类步骤留到阶段 4.5**：规划里标 **[文档]** 的步骤（ADR、交接文档、下一阶段计划、README、CHANGELOG、验收用例表、使用说明）**一律跳过**，先做完代码步骤直接进阶段 4。直接用 `PLAN-*.md` 时这类节常排在末尾，按编号顺序做会落在审查之前——这是错的。跳过时当场 `TaskCreate` 记一条「阶段 4.5 文档收尾：§2 步骤 7、8」。**例外**：本轮任务本身就是写文档（没有代码改动），正常做
- **子代理返回后**：跑 `route-check --from <开工时间戳>`，❌ → S7（第一个包就核）；跑验证命令看结果；它报「已清理 / 已还原 / 无残留」→ **自己核**：grep 那个具体的修改点，查可能漏掉的残留位置（数据库关联表、生成的目录），别拿 `git diff` 总行数当证据；按 P7 收工 → 新起一个接力，被限流打断 → SendMessage 续；报告里有需用户执行的命令（P10 攒下的）→ 记一条「末尾交给用户：<命令>」（TaskCreate 不可用就写进 `.route-plan.md` 末尾），阶段 5 清理前一次交出，用户执行后主会话重跑一遍 P3 的验证命令，再出最后汇报；报缺凭据 / 缺前提（S5）→ 问用户要，不许自己绕，也不许记成「未验证」就往下走
- **方向性分歧（S3）**：子代理要改变规划里的方案、接口、数据结构、文件范围，或推翻用户在阶段 2 的答案，或报告规划的做法走不通（P9）；它已经自作主张改了、只在报告里带一句的同样算。**停下来**，用 `AskUserQuestion` 给出「规划原文 / 子代理的提议 / 各自的后果」→ 用户定了，把决定写进规划（本会话有 planner 就 `SendMessage` 让它改，没有就按阶段 2 按改动量处理）→ 再按修订后的规划派活；已被自作主张改掉的部分，按用户的决定保留或返工

## 阶段 4：审查与修复（opus）

实现完**自动**启动 `code-reviewer`（不传 model），不问用户要不要审。界面小改和判成「微」的改动**攒批审**：不为一处单独起审查，攒着和下一批一起审，最晚在给用户提交脚本或定档之前审一次；本轮只有这类小改时，审查范围就是这几处。审还是要审。

**启动时一次给足四样**：① **改动范围**：git 仓库给 `git diff`，否则逐个列文件，能精确到函数名或行号区间就给；② **规划文件路径**：否则会把「规划要求的做法」误报成缺陷。有「修订补充」时**两份都给**，注明冲突处以修订补充为准、那是用户的决定——不然审查员会把用户改过的地方报成「与规划不符」的 🔴，被直接修回去；③ **本轮明确不管的部分**：只放规划或用户明确延后的，**别放自己没验证过的推断**（「这个分支不可达」「这是死代码」）；④ **实现子代理已经自查过什么**：跑了哪些测试、验证过哪些边界。范围聚焦本次改动，但周围的代码和调用方必须一起看。**绝不为了快而压缩审查**。

**拿到结果：先核模型，再落盘，再完整列出**：① 跑 `route-check --from <开工时间戳>`，❌ → S7，别在跑错模型的审查上继续修；② **写成文件** `<项目根>/code-review-<YYYYMMDD-HHMM>.md`（审查员不能写文件，由你写）；③ **在终端用表格完整列出，一条都不许省**：

| 编号 | 严重度 | 位置 | 问题 | 触发场景 | 建议 |
|---|---|---|---|---|---|
| R1 | 🔴 | `src/a.ts:42` | 具体缺陷 | 什么输入 / 状态导致什么错误结果 | 怎么改 |

「触发场景」不许空或含糊，它是判断真伪的唯一依据。只报数量和严重度等于什么都没说。

**先把 🟡 交给用户（S4）**：表格之后写你对每条 🟡 的判断（该修 / 可以不修 / 为什么），再用 `AskUserQuestion` 让用户选修哪些。🔵 一句带过，用户也可以点名要修。**不许因为「改动小」「显然该修」就自己动 🟡。** 用户答完，把选择**追加到审查报告末尾**的「用户在 S4 的选择」（修哪些、不修哪些），续跑靠它接上。

**修复：一批修完，复审一次**：
1. 🔴（必修）+ 用户批准的 🟡（+ 点名的 🔵）**一起**派修复子代理：`model: "sonnet"`，prompt 给审查报告路径和要修的编号，带 P1–P10。派完结束回合等它们时，按【主会话分工】看要不要附压缩命令
2. 修完 `SendMessage` 发回**同一个** `code-reviewer`：「已按 R1、R3 修改（改了 `文件:行`……），请复审」
3. 复审的新发现编 **N1、N2…**。**每一轮复审结果都追加进同一份 `code-review-*.md`**（阶段 4.5 的文档子代理只能读文件），追加完之后第一次结束回合时同样看要不要附压缩命令
4. 复审出新的 🔴 → 直接修，再复审；新的 🟡 → 照样先问用户
5. **收口**：本轮没改脚本行为（只动 `.md` / 措辞）→ 只审一轮，🟡 照修，只剩 🔵 就收口，把剩下的 🔵 写进报告「没修的及原因」由用户定；改了脚本 / 配置 → 最多审 2 轮，第 3 轮的发现写进下一轮待办，不在这轮修
5. **两轮后仍有 🔴（S6）** → 停下来如实说卡在哪，不要无限循环

审查结束后，因为用户提意见又改的代码，同样送同一个 `code-reviewer` 复审。审查员被 429 / 503 打断 → `SendMessage` 续同一个，不重开。

**用户说「超过 N 分钟就留到下一轮」**：这是**延期，不是砍范围**，一条都不删。被问耗时给实测数字和依据，别为了让他同意往低了报。用户明确说要修的 → 标「已拍板、下一轮必修」；用户还没表态的 🟡 → 标「**待用户决定（🟡）**」，下一轮照样问，**不许标成已拍板**；留档要能独立看懂：每条的位置、触发场景、改法整段抄进交接文档（只留审查报告路径不够，它可能被 `.gitignore` 排除）。

## 阶段 4.5：文档收尾（审查和修复都结束后）

代码定稿了才写阶段 3 跳过的文档。派 `model: "sonnet"` 的文档子代理，prompt 带 P1–P10 中适用的几条（至少 P2、P5、P6、P7），并给足：

1. 跳过的文档步骤清单（阶段 3 记下的那条）
2. **审查报告路径** + 修掉了哪几条（R×、N×）——文档描述的是**修复后**的最终状态
3. 判定不修的 🟡🔵、以及用户决定先写文档时仍未修的 🔴 → 作为已知问题写进交接文档；用户还没表态的 → 标「待用户决定」
4. **交接文档末尾已有的新需求**（阶段 0 写进去的）→ 告诉它**保留原样，不要重写那几条**
5. **`.route-plan.md` 里对 `PLAN-*.md` 的修订补充**（如有）→ 并进原规划的对应节（或项目的交接文档 / 下一阶段计划），让下一轮读到的规划和代码一致

派活前核一遍：prompt 里每一处「以 X 文件为准」，X 里**真的**有那些内容。文档子代理报「某条找不到」→ 先查自己给的源文件漏没漏，补上后 `SendMessage` 让它接着写；它宁可交白也不编，这种行为要在汇报里明确肯定。文档写完后代码不该再动；如果还要改，改完送审查复审，再同步文档。

## 阶段 5：清理

- **删过程文件一律用** `node ${CLAUDE_PLUGIN_ROOT}/route-clean.js <过程文件所在目录> [文件名…]`。要单独一次调用：前面不拼 `cd …&&`，后面不接管道或重定向，路径逐字照抄，这样才能命中安装器装的放行规则。不给文件名就删该目录下全部过程文件。它只删 `.route-plan.md`、`.route-plan-*.md`、`.route-handoff-*.md`，被 git 跟踪的跳过。直接 `rm` 在 auto 模式下会被分类器拦。阶段 0「丢弃」、阶段 2 删 `.route-plan-redesign.md` 也用它。**被拦或报错 → 把这条命令原样交给用户跑，别换写法绕**
- 确认全部完成后，删 `.route-plan.md`、`.route-plan-redesign.md`（如果还在）和已完成包的 `.route-handoff-*.md`。规划备份 `*.bak-<时间>` **不删**，汇报里列出路径。`.route-plan.md` 若装着对 `PLAN-*.md` 的修订补充，删之前先 grep 核实每条都已并进去（阶段 4.5 第 5 条）
- 还有没做完的包 → 先把剩余事项抄进交接文档，告诉用户，再删
- `code-review-*.md` **保留**，提示可加进 `.gitignore`
- **不 commit、不 push**

## 最后汇报

1. **问题**：本轮要解决什么（一两句）
2. **解法**：改了哪些文件、要点；**决定清单**——每个决定 + 谁定的（用户在阶段 X 答的 / planner 第 5 节写明的 / 用户亲口授权的）。没有「编排者自己定的」这一类；真有，标出来并说明
3. **现状**：审查报告路径、修掉了哪几条（引用编号）、没修的及原因；交给你执行的命令（执行了没有、重跑 P3 的结果）；还剩什么没解决 / 没能验证的部分（没跑测试就说没跑，拿不准就说拿不准）；文档收尾写了哪几份，确认反映的是修复后的代码；清理情况，以及工作区里**未提交的改动清单**（提不提交由用户决定）
4. **模型核对**：跑 `node ${CLAUDE_PLUGIN_ROOT}/route-check.js --from <开工时间戳>`（不带完整表参数）。没有 ❌ 和 ⚠ 就写一句「模型核对通过：规划 N · 审查 N · 其余 N，全部按设计跑」，三个个数照抄 route-check 那一行括号里的（是子代理个数，不是调用次数），个数为 0 的写「本轮无」或「本轮跳过」，如「模型核对通过：规划 0（本轮跳过）· 审查 1 · 其余 1，全部按设计跑」；那一行写的是「窗口内还没有子代理」就写「模型核对通过：本轮没有子代理」；有 ❌ 或 ⚠ 就只贴那几行问题行和结论行

第 2、3、4 条不许省。**不写**模型构成、花费、token 用量、EIU、$ 估算、调用次数这类用量统计（第 4 条照贴的问题行里带的数字不算）；用量要看自己跑 `node ${CLAUDE_PLUGIN_ROOT}/usage-audit.js`。
